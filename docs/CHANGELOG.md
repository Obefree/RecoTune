- **Studio (задержка записи, #5):** фикс «ставишь задержку X, а следующую дорожку надо сдвигать на 2X, и то через раз». Двойного применения сохранённого `offsetMs` не было — двоилась **латентность на входе записи**: бэкинг запускался `playAsync()` (без ожидания), а `rec.startAsync()` стартовал сразу, и микрофон писал ещё и «холодный старт» плеера (≈ величина самой задержки) поверх латентности железа. Компенсировался только `prerollMs` → приходилось руками ставить ~2×; холодный старт плавал → «иногда норм, иногда снова удвоить». Фикс: запись стартует **только после того, как бэкинг реально зазвучал** (`waitForPlaybackStart`, потолок 500 мс), холодный старт не пишется, остаётся 1× латентность железа, которую и компенсирует единственный `offsetMs = prerollMs`. Одно место владеет компенсацией; правка внутри `recordTrack`, без второго пути. См. [docs/features/2026-07-05-studio-record-latency-double-fix.md](./features/2026-07-05-studio-record-latency-double-fix.md).
- **Melody (странное распознавание + воспроизведение, #4):** убрана причина «то хорошо, то плохо от прогона к прогону» — мелодия гоняла **два** детектора (контур `melodyTranscription` + классику `SungNoteDetector`) и **скрыто переключалась** между ними по порогу уверенности, а у них разный timebase. Схема схлопнута в **одну** (контур = source of truth, D15): убран `recognitionMode`, флип по `isTranscriptionConfidenceOk` и живой `SungNoteDetector` из `useSungNoteHistory` (детектор остаётся только в Тюнере). Такты/продолжительность выровнены — нотный стан и PLAY индексируются 1:1 с сегментами (`buildStaffPlaybackTimings` без лишней группировки 60 ms). Фикс слияния: короткая **другая** нота между двумя одинаковыми (`A–C–A`) больше не поглощается в `absorbShortFragments`. `npm run verify-melody-transcription`. См. [docs/features/2026-07-05-melody-single-path-timebase-merge.md](./features/2026-07-05-melody-single-path-timebase-merge.md).
