# Studio: запись овердаба больше не требует «удвоить задержку» (#5)

**Дата:** 2026-07-05

## Жалоба (Alex, #5)

Ставишь задержку X, пишешь **следующую** дорожку — и её приходится сдвигать на **2X**,
чтобы попала в такт. Иногда нормально, иногда снова надо удваивать. Значит компенсация
латентности применяется несогласованно между «монитором во время записи» и финальным
сведением: записанная дорожка приезжает так, будто ей нужна двойная задержка.

## Где именно задержка удваивалась

`src/screens/StudioScreen.tsx`, `recordTrack`.

Компенсация латентности в Studio — **одна величина**: дорожки 2+ сохраняются с
`offsetMs = prerollMs`, и на воспроизведении/сведении дорожка сдвигается раньше ровно на
неё (`playAll`, `handleMasterSeek`, WebView-микс — все три пути согласованы между собой).

Проблема была в **старте записи**:

```
playbackSounds.forEach(... s.playAsync() ...);  // запустили бэкинг (fire-and-forget)
await rec.startAsync();                          // и сразу стартуем микрофон
```

`playAsync()` не ожидается, и у плеера есть «холодный старт» (заполнение буфера ≈ величина
самой латентности). Микрофон же стартовал практически сразу → в записанный файл попадал и
этот холодный старт плеера **как дополнительный лид**. Итог: реальная задержка записанной
дорожки ≈ `prerollMs` (латентность железа) **плюс** ≈ `prerollMs` (холодный старт плеера),
а сохранялось `offsetMs = prerollMs` — компенсировалась только половина, и пользователю
приходилось руками ставить ~2X. «Холодный старт» варьируется от запуска к запуску → «иногда
нормально, иногда снова надо удваивать».

То есть двойного **применения** сохранённого offset нет — двоилась **латентность на входе**
записи (baseline preroll стекался поверх незакомпенсированного старта плеера), ровно как в
гипотезе «recording start isn't compensated → new track shifted by playback latency → manual
delay stacks on top».

## Что сделано

| Файл | Изменение |
|------|-----------|
| `src/screens/StudioScreen.tsx` | Добавлен `waitForPlaybackStart(sound, startMs)` — ждёт, пока бэкинг реально начнёт играть (позиция ушла дальше предпозиционированного старта), с потолком 500 мс, чтобы никогда не подвесить запись. |
| `src/screens/StudioScreen.tsx` (`recordTrack`) | После запуска бэкинга и **до** `rec.startAsync()` ждём реального старта опорной дорожки (первая с `offset ≥ 0`). Микрофон стартует под уже звучащий бэкинг → холодный старт плеера не пишется, остаётся только латентность железа, которую и компенсирует единственный `offsetMs = prerollMs`. |
| `src/screens/StudioScreen.tsx` (комментарии) | Обновлён устаревший комментарий про `prerollMs` (описывал старую timing-preroll схему «ждать после старта записи перед плеером», которой в коде уже нет). Явно зафиксировано: компенсацией латентности владеет **одно место** — сохранённый `offsetMs`. |

Ничего нового не плодилось: правка внутри существующего `recordTrack`, один маленький
helper, второй путь компенсации не добавлялся, мёртвого кода не оставлено.

## Было → стало

| | Было | Стало |
|--|------|-------|
| Старт записи | бэкинг `playAsync()` (не ждём) → сразу `rec.startAsync()` | бэкинг стартовал → ждём реального звучания → `rec.startAsync()` |
| Латентность записанной дорожки | ≈ железо + холодный старт плеера (≈ 2×) | ≈ только железо (1×) |
| Нужный offset после записи | ~2 × заданной задержки, нестабильно | ≈ заданная задержка, стабильно |
| Владелец компенсации | размыт (offset + незакомп. старт) | одно место — `offsetMs = prerollMs` |

## Проверка

- `npx tsc --noEmit --skipLibCheck` — чисто.
- Отдельного studio-теста в репозитории нет; логика записи (нативный expo-av + реальный
  микрофон/латентность устройства) проверяется только на телефоне.

**На устройстве (нужно для полного подтверждения):**
1. Настройки → задать задержку X (напр. 150 провод).
2. Записать дорожку 1 (минус/гитара), затем записать дорожку 2.
3. Play all: дорожка 2 должна попадать в такт **без ручного удвоения** до 2X.
4. Записать дорожку 3 — тоже без повторного удвоения; результат стабилен от записи к записи.

## Ограничения (честно)

- Точное значение задержки под конкретное железо/BT всё равно калибруется слайдером
  «Задержка дорожек»: софт не измеряет round-trip латентность железа (нет loopback), он лишь
  перестал добавлять к ней холодный старт плеера. Ожидание старта ограничено 500 мс —
  если статус плеера почему-то не отдаёт прогресс, запись стартует как раньше (не хуже).
